# 会話の解説を「登録しといて」で登録する

この文書はChatGPTのChat mode・Work modeのどちらからも使う。対象は `KKawamura1/care-manager-quest` の `main`。アプリからコピーした問題文の末尾に、この文書へのリンクと登録先を識別する対象情報（JSON）が含まれる。

## 許可

ユーザーの2026-10-18の指示により、対象が明確な会話で「登録しといて」「この解説を登録して」等と依頼されたら、**解説JSONを1ファイル追加するmainへの直接コミットを許可する。PR・人のレビュー・追加の承認は求めない。** ルートの [AGENTS.md](../AGENTS.md) にも同じ許可を明記している。

この許可は `data/explanations/entries/<UUID>.json` の新規追加だけ。解説を求められただけでは書き込まない。接続先の権限や現在のツール制限を回避するための許可ではない。

## 登録の最短手順

1. 会話の直近の対象を確認する。登録先の対象情報の `schemaVersion`、`questionId`、`questionVersion`、`choiceId`、`cardRevision`、`questionRevision` は、**存在する項目をそのまま引き継ぐ**。2020年度の `care_manager_2020_NNN` を `2020-NN` に変更しない。選択肢IDは対象情報の文字列IDを使う。
2. 既に会話で説明した内容を、選択肢なら80〜180字程度、問題全体なら150〜300字程度に要約し `explanation` に入れる（上限600字）。正誤の理由、誤りの訂正、制度改正の区別など、今回の理解に必要な点を残す。未確認の説明や新たな推測を足さない。試験当時と現在を扱った会話なら、要約でも時点を混ぜない。
3. 新しい小文字のUUID v4を1つ作り、`registrationId` とファイル名に同じ値を使う。実際の登録日時をUTCの `registeredAt` に入れる。この操作のリトライ中は同じUUIDを使う。出典が会話で確認できれば `sources` にタイトルとHTTPS URLを加える。出典が不明ならURLを創作せず省略する。
4. GitHubの **create_file** を使い、`repository_full_name: KKawamura1/care-manager-quest`、`branch: main`、`path: data/explanations/entries/<UUID>.json` を指定して追加する。コミットメッセージは例 `explanation: 2021-10 choice 4`。既存索引やアプリのコードの更新、clone、ローカルビルド、PR作成は不要。
5. 追加結果の成功とcommit SHAを確認する。可能なら同じファイルをmainから再取得し、保存内容も確認する。成功後は「2021年度 問10・選択肢4に登録しました」のように対象とコミットへのリンクだけを短く返す。**コミット成功は登録完了、画面への反映はCloudflareの自動ビルド・配信後**。デプロイを確認していなければ「本番反映済み」とは言わない。

解説への回答は通常の文章で行い、登録用JSONを回答へ出力しない。登録時の要約・JSON生成・GitHubへの追加はChatGPTが行う。ユーザーに解説やJSONのコピー・アプリへの貼り付けを求めない。

### JSONの例

以下は形式の例であり、IDや改訂印は実際の会話の対象情報から取得する。例の値をそのまま登録しない。

```json
{
  "schemaVersion": 1,
  "questionId": "2021-10",
  "questionVersion": 1,
  "choiceId": "4",
  "cardRevision": "1234abcd",
  "explanation": "試験当時の条件に沿った正誤の理由と、今回確認した覚えるポイント。",
  "registrationId": "a73f6842-9d51-4ab6-a831-f7d3b428c160",
  "registeredAt": "2026-10-18T06:24:10Z",
  "sources": [
    {
      "title": "介護保険法",
      "url": "https://www.mhlw.go.jp/web/t_doc?dataId=82998034&dataType=0"
    }
  ]
}
```

問題全体への登録は `choiceId` と `cardRevision` を省略し、対象情報にある `questionRevision` を使う。個別選択肢の解説を無理に問題全体の解説へ変更しない。選択肢ごとの登録は○×学習だけでなく、5択の採点後・解答済み問題の詳細でも読める。

## 競合・再試行・訂正

- 登録ごとに別のUUIDファイルを追加するため、別の会話と同じ一覧ファイルを編集しない。**同じカードに複数の登録があっても両方残る**。有効な版が一致するもののうち `registeredAt` が最新のものを表示し、同時刻ならUUIDの降順で決定する。以前の登録も画面で開ける。
- 内容の訂正・追記も新しいUUIDで1ファイル追加する。既存レコードの上書き・削除・force pushはしない。
- `create_file` が409/422等を返す、または成功したか不明なときは、まず**同じUUIDのパスをmainから読む**。同じ内容が既にあれば再登録せず成功として扱う。なければ最新main上で同じファイルの追加を再試行する（目安3回まで）。同じUUIDに別の内容がある衝突の場合だけ、新UUIDを発行する。認証・接続・権限エラーは競合として再試行しない。
- Git data APIしかない場合は、最新mainのcommitとtreeを取得し、そこへ新規1ファイルだけ追加したtree、最新mainを親とするcommitを作り、`expected_sha`付きでmainをfast-forwardする。mainが進んでいたら最新treeから作り直す。古いtreeで他の追加を消したりforceで進めたりしない。
- 改訂印がない、または複数の問題のどれを指すか不明な場合は、対象だけを確認する。改訂印を推測しない。旧形式の○×JSONにある `cardRevision` はそのまま使用できる。旧形式の問題全体JSONで `questionRevision` がない場合は、アプリの「問題をコピー」で新しい対象情報を取得してもらう。

## 反映と自動検証

- アプリはこのディレクトリを自動で読み込む。索引や集約JSONは不要で、1回の登録は1ファイル追加だけで済む。
- 対象のID・版・改訂印が現在の問題と一致する解説だけ表示する。本文や判定が改訂された古い解説は表示しない。学習履歴は変更しない。
- mainへの登録はGitHub Actionsの軽量な登録検証と、Cloudflareの型チェック・単体テスト・ビルドを起動する。解説追加だけなら人手によるテスト実行・レビュー待ちは不要。機械チェックの失敗が判明したら、登録済みと配信済みを区別して伝える。
- GitHubの書込みツールがない場合は登録できない。別の会話へ内容を渡す場合には、本書URL・対象情報・会話で説明した内容を引き継ぐ。ユーザーに全問題や会話全体の貼り直しを求めない。
